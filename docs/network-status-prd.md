## 1. 背景与问题

ATOM 是一台通过 WiFi 联网的嵌入式训练设备，上课时通过 TRTC 进行实时音视频互动（含摄像头画面上行）。当前用户反馈的核心问题：**设备已连上 WiFi，但上课时仍然卡顿**。

- 「已连接 WiFi」≠「网络够用」。信号衰减、家庭宽带上行不足、路由器负载等都会导致卡顿，但设备目前对用户只呈现「已连接」一种状态；
- 用户卡顿时无法归因，默认判定为「阿童木做得卡」，产生客诉；客服排查也缺少依据；
- ATOM 是固定摆放设备，信号好坏在摆放时即已决定，但用户没有任何工具能发现「摆放位置信号弱」这一问题。

### 1.1 现有机制及其问题

设备目前已有若干网络慢 / 异常提示，但全部是**课中真的出了问题之后**才触发的弹窗，且部分弹窗需要用户手动点击确认才能关闭。这带来三个问题：

- **时机太晚**：提示出现时体验已经受损，用户没有任何机会在课前预防；
- **形式太重**：阻断式弹窗遮挡训练画面，把「网络卡」升级成「课被打断」；
- **操作不可行**：用户正在做训练动作、距屏幕较远，要求手动点确认基本等于强制中断训练——提示本身成了负体验。

> 因此本方案不只是「新增红绿灯」，同时要**收敛存量课中弹窗**：把网络提醒从「课中事后打断」改造为「课前可预防、课中不打断」。

## 2. 目标与非目标

### 2.1 目标

- **可感知**：用户在任意时刻都能一眼看到当前网络对上课「够不够用」（红绿灯三态）；
- **可验证**：用户可以主动发起一次网络验证，获得针对上课链路的真实测速结果；
- **可行动**：网络差时给出可执行建议（靠近路由器 / 切换 WiFi / 重测），而非只报忧；
- **不打断**：课中网络提示全部改为非阻断、自动消失、零操作；需手动确认的弱网弹窗全部移除；
- **可归因**：质量数据上报云端，支撑客服排查与阈值校准，降低网络类客诉。

### 2.2 非目标

- 不承诺「解决」用户的网络问题（宽带质量不在我们控制内），本期解决的是感知、归因与引导；
- 不做持续带宽测速（会挤占上课带宽）；不做路由器侧诊断与配置；
- 课中自适应降级（流畅优先、音频优先）依赖 TRTC 既有能力，本 PRD 只要求正确配置并在文案中告知用户，不新增自研弱网算法。

## 3. 方案总览

一套「红绿灯」状态机 + 一个网络验证小程序，通过四个触点触达：

1. **上拉通知栏**（设备）：常驻网络状态条目，点击进入网络验证小程序；
2. **WiFi 图标与 WiFi 菜单**（设备）：控制中心 WiFi 磁贴角标 + WiFi 设置页状态行；
3. **网络验证小程序**（设备）：独立小程序，秒开当前状态 + 可发起完整测速；
4. **手机 App 课中提示**：训练页面同步展示网络状态，并归因到「手机侧 / Atom 侧」。

所有触点共享同一个状态机语义与阈值，保证任何入口看到的灯色一致。与现状的关系一览：

| 维度 | 现状 | 本方案 |
| --- | --- | --- |
| **触发时机** | 课中已经出问题才提示 | 常驻可见 + 课前可验证 + 课中实时 |
| **提示形式** | 阻断式弹窗，遮挡训练画面 | 常驻灯色 / 角标 / 自动消失 toast |
| **用户操作** | 部分需手动点击确认 | 零操作；仅「需用户决策」的场景保留弹窗 |
| **问题定位** | 无归因，只报「网络异常」 | 分段归因（设备→路由器 / 宽带→公网）+ 可执行建议 |

### 3.1 灯的三态定义（字形：三格 bars）

颜色三档（绿 / 黄 / 红）搭配三格阶梯 bars 作为统一字形：**3 格绿 / 2 格黄 / 1 格红**——格数 + 颜色双通道编码，色盲与小尺寸下仍可读；阶梯形与 WiFi 扇形（= 本地信号强度，用于网络详情页）明确区分；圆点方案另有一个否决理由——**与摄像头设备上「录制中 🔴」的红点语义冲突**，红色圆点极易被误读为正在录制。对比论证见 [`quality-icon-exploration.html`](./quality-icon-exploration.html)。

| 灯色 | 含义 | 行为 |
| --- | --- | --- |
| 绿 · 网络良好 | 上课体验预计流畅 | 静默显示，不打扰用户 |
| 黄 · 网络一般 | 可以上课，可能偶尔卡顿 | 课中触发流畅优先降级并轻提示 |
| 红 · 网络较差 | 上课大概率卡顿 | 提示并给出可执行建议 |

### 3.2 检测数据源分工

| 场景 | 数据源 | 频率 | 流量成本 |
| --- | --- | --- | --- |
| **常驻**（通知栏 / WiFi 图标 / WiFi 菜单） | 系统 RSSI + ping 网关与自家服务器 | 30 秒静默刷新 | 几乎为零 |
| **主动验证**（小程序完整检测） | TRTC `startSpeedTest`（到 TRTC 边缘节点） | 用户触发，单次约 15 秒 | 少量真实测速流量；**课中禁止调用** |
| **课中** | TRTC `onNetworkQuality` + `onStatistics` | SDK 每 2 秒回调 | 零（复用业务流量） |

> 原则：**不为了检测而挤占上课带宽**。常驻状态只用被动/轻量数据；真实测速只在用户主动发起且不在课中时执行。

## 4. 功能需求

### F1 上拉通知栏 · 常驻网络状态（P0）

- **F1.1** 上拉通知栏顶部新增**常驻**网络状态条目，位于所有通知消息之上，不可清除；
- **F1.2** 条目内容：灯色圆点 + 一句话结论（见 §6 文案表）。数据来自常驻检测（30 秒刷新），展开通知栏时立即触发一次刷新；
- **F1.3** 点击条目跳转进入**网络验证小程序**（F3），小程序自动开始一次快速验证；
- **F1.4** 课中不显示通知栏入口的弹出提醒，仅保留条目本身（课中提醒由 F4 负责，避免双重打扰）。

### F2 WiFi 图标与 WiFi 菜单 · 红绿灯（P0）

- **F2.1** **控制中心 WiFi 磁贴**：黄 / 红时在磁贴内 WiFi 图标右侧显示小型三格 bars（2 格黄 / 1 格红）；绿灯不显示，图标回到居中（不给正常状态加噪音）。**决策记录——不用图标弧格填充度 / 染色表达质量**：弧格填充度的既定语义是信号强度（RSSI），而 bars 表达的是综合网速质量，两者在「信号满格但宽带拥塞」时背离，复用填充度必然误导（满格红色令人困惑，降格显示则谎报信号）；图标染色会与磁贴的开关语义打架。也不用右上角角标圆点：与全系统 bars 字形不一致，且 17px 角标位过小。弧格填充度保留给网络详情页（ⓘ）表达真实 RSSI。对比论证见 [`quality-icon-exploration.html`](./quality-icon-exploration.html)；
- **F2.2** **WiFi 设置页状态行（锚定已连接网络）**：已连接网络自动置顶到 WiFi 开关正下方（iOS 式动态排序），**状态行紧贴已连接网络行下方**——灯描述的就是这个网络，位置即语义，与手机端「灯随用户画面」（F6.2）同一原则；其余曾配网络归入分隔线下的「其他曾配网络」分组。样式：三格 bars（灯色）+ 网速状态 + 弱化灰色「测速 ›」，无卡片底、无描边。文案三态：**网速良好 / 网速一般 / 网速较慢**；「测速 ›」三态恒显——状态行是本页测速的唯一入口，恒显保证可发现性。位置演进记录见 [`wifi-status-placement-exploration.html`](./wifi-status-placement-exploration.html)；
- **F2.2a** 状态行整行为点击热区（高度 ≥ 60px），文字虽小、热区不小；
- **F2.3** 点击状态行进入网络验证小程序（F3）；
- **F2.4** 状态行锚定于「已连接网络」行，随其存在而存在：**WiFi 关闭或未连接 → 无已连接行，状态行不显示**（未连接由列表自身表达——没有 ✓ 行）；连接中 → 在对应网络行内显示「连接中…」；**已连接但暂无有效数据**（首次进屏 / 刚连上 / 缓存过期）→ 三格全暗 +「检测中…」；有数据 → 三色网速状态。控制中心磁贴 bars 仅在「已连接且黄 / 红」时显示；
- **F2.4a** **静默刷新不显示「刷新中」**：后台 30 秒一次的常驻刷新直接原地更新灯色与文案，不出现任何加载态——否则这行每半分钟闪一次「刷新中」，本身就成了噪音。「检测中…」仅在 F2.4 定义的「无有效数据」时出现；
- **F2.5** 系统状态栏若展示 WiFi 图标，黄 / 红时图标同步染色（与磁贴同一状态机）；
- **F2.6** **连接流程系统逻辑（开发对接）**：(a) 开启 WiFi 开关 → 进入**扫描状态**（列表显示扫描中）；(b) 扫描完成 → 系统自动从「曾配对网络」中选择合适网络连接；(c) 连接成功 → 列表**轻刷新动效**：当前连接的网络上浮置顶到 WiFi 开关正下方，随后其下方跟上网速状态行（暂无有效数据时先显示「检测中…」，出数据后变为三色 bars + 网速状态）；
- **F2.7** **图标下方文字调整（开发对接）**：原图标下方的「WiFi」标题为无效信息，改为**「常见网络问题」**；该行文字**可点击**，点击跳转到连接帮助 tips 页面。

### F3 网络验证小程序（P0）

- **F3.1** 独立小程序，出现在应用列表中；F1 / F2 的入口均跳转至此；
- **F3.2** **首页 = 纯入口（测速前）**：仅展示灯色 bars + 一句话结论（来自常驻检测缓存，进入即触发一次轻量刷新）+ 主按钮「测速」；**不展示任何数字指标**——常驻轻探测只有延迟 / 丢包、没有真实带宽，放数字会让旧数据被误读为实测结果。数字指标仅在测速后的结果页出现，「测速前 = 入口、测速后 = 报告」两种状态因此天然可区分；**副行显示数据时效**：「刚刚更新」（≤60 秒）/「N 分钟前更新」（≤5 分钟）——回答「这个结论是多久之前测的」；缓存超过 5 分钟视为过期，**不显示旧灯色**，结论区直接显示「检测中…」并立即刷新（采样调度见 F7）；
- **F3.3** **完整检测**：点击「完整检测」按钮调用 TRTC `startSpeedTest`（参数与结果映射见 §5.1：延迟 + 带宽双测，期望上行 1500 kbps / 下行 2000 kbps），测速目标为上课真实链路（TRTC 边缘节点）。检测中沿屏幕边缘展示环形进度（按官方回调真实驱动），约 10–20 秒，可取消；检测中按钮置灰防重入（官方限制同一时间仅一个测速任务）；
- **F3.4** **结果页三态**（绿 / 黄 / 红各有独立结果页）。黄 / 红结果必须包含三层信息：**影响**（对上课意味着什么——黄：动作识别可能偶尔延迟；红：动作识别与计数可能延迟、画质下降）、**归因**（弱在哪一段：本机→路由器 / 路由器→公网）、**建议**（怎么办）；按钮遵循 F3.7；
- **F3.5** **课中互斥**：正在上课时禁用完整检测，按钮置灰并提示「下课后可用」，只展示课中实时数据；
- **F3.6** 每次完整检测的结果记录本地最近 10 次（按 SSID 分组），并上报云端（F5）；小程序内提供「历史记录」次级入口（P2，会议提出，支撑「过去一段时间综合网速」的查看）；
- **F3.7** **按钮逻辑**：主按钮 = 当前状态下的最短解决路径——

| 状态 | 主按钮 | 次按钮 | 理由 |
| --- | --- | --- | --- |
| 首页（任意灯色） | 测速 | — | 本页唯一动作 |
| 检测中 | — | 取消 | 15 秒等待可中止 |
| 结果 · 绿 | 完成（点击退出） | 重新检测 | 没有问题，最短路径是离开；用户多因「刚才卡了」而来，对绿结果存疑可就地复测 |
| 结果 · 黄 | 重新检测 | 完成 | 建议是软动作（暂停其他下载），做完就地重测验证 |
| 结果 · 红 | 去 WiFi 设置 | 重新检测 | 建议是硬动作（换网 / 挪设备），主按钮直达解决路径；什么都不改就重测，结果不会变——不解决问题的动作不占主位 |
| 结果 · 失败 | 重新检测 | 完成 | 测速任务未完成，重试是唯一有效动作 |

- **F3.8** **报告卡（波形 + 四指标一体）**：波形与延迟 / 丢包 / 下行 / 上行四个指标合并为一个带底色的卡片容器——检测中卡内实时绘制双曲线（蓝 = 下行、绿 = 上行，每 2–3 秒一个样本点，见 §5.1），检测结束波形定格保留在结果页卡内，四指标在其下一行排开（下行 / 上行标签带曲线同色标记，替代独立图例）。**一张卡 = 一份完整测速报告，用户截图即可反馈给客服**（与 F5 上报互补：截图给人看，上报给系统看）；卡内字号整体缩小——这是可近距操作的 UI，信息密度优先于远读性。稳定性派生标签规则不变：样本方差超阈值时卡下方显示「网络波动较大」；
- **F3.9** **界面精简**：小程序各页面移除顶部时钟——与检测任务无关的信息不上屏；
- **F3.10** **状态机（对齐 §5.1）**：首页 →「完整检测」→ **检测中**（环形进度按节点回调 `finishedCount / totalCount` 推进，标注「节点 N / M」；波形逐样本生长；「取消」调用 `stopSpeedTest` 回首页）→ `onSpeedTestResult`：**success** → 按 `quality` 进入绿 / 黄 / 红结果页；**失败** → 失败态（「检测未完成 · 请重试」，不给任何灯色——没测出来 ≠ 网络差；`errMsg` 仅上报）。结果页「重新检测」直接回到检测中；
- **F3.11** **信息分组规范**：结果页从上到下四组——**① 结论**（bars + 一句话）→ **② 报告卡**（波形 + 四指标一体，数据来自 `rtt`、`lostRate` 较大值、`availableDown/UpBandwidth`，-1 显示「—」；不达期望值的项用灯色着色）→ **③ 影响 + 建议**（仅黄 / 红）→ **④ 操作**（主 + 次按钮）。卡片边界承担分组职责，组间距大于组内距，一组只说一件事。

### F4 课中实时角标、弱网提示与存量弹窗收敛（P1）

- **F4.1** 课中以 TRTC `onNetworkQuality` 为唯一灯色数据源（每 2 秒回调，上行 `localQuality` 与下行 `remoteQuality` 取较差者）；
- **F4.2** 绿灯时角标**完全隐藏**；变黄 / 红时在屏幕顶部显示三格 bars 角标（2 格黄 / 1 格红）；
- **F4.3** 灯色下降时弹出一次 toast，文案区分方向：上行差 →「老师可能看不清你的画面」；下行差 →「课程画面可能卡顿」；黄灯统一为「网络一般，已自动降低画质」；
- **F4.4** 确认 TRTC 弱网降级配置：`setNetworkQosParam` 流畅优先、音频优先兜底、上行编码参数留余量（720p），降级动作通过 F4.3 文案让用户可感知；
- **F4.5** 课中每 2 秒的 `onStatistics` 明细（RTT / 上下行丢包 / 码率）聚合后随课程会话上报（F5），不在 UI 展示；
- **F4.6** **存量弹窗收敛**：盘点现有课中网络类弹窗，按「是否需要用户决策」分级——仅「彻底断线且无法自动恢复、需用户选择重连 / 退出」类保留阻断式弹窗；其余全部替换为本方案的角标 + 自动消失 toast；**移除所有需手动点击确认的弱网提示**；
- **F4.7** **提示可感知性**：训练中用户处于动作中、距屏幕较远，视觉 toast 可能看不到——黄 / 红提示同步配一个短音效或简短语音播报（如「网络不稳定」），确保不看屏幕也能感知；音量跟随媒体音量，可在设置中关闭；
- **F4.8** **课中带宽保护（会议决议 2026-07-07，可立即执行）**：课中实时 AI 识别期间**暂停一切后台大文件上传**（组间报告 720p 视频等）——识别的实时性优先于组间报告的即时性，这是已拉齐的取舍原则。set 结束 / 组间休息期尝试上传；一旦检测到重新进入课中，**取消排队中的后续上传**（当前文件传完即止；断点续传列入后续版本）。组间报告界面同步展示「视频上传 / 解析中，稍后或课后回看」，不承诺练完即看。Record / Log 模式的推流与 SD 卡存储策略超出本 PRD，另行文档。

### F4-R 存量弹窗 Review 与收敛规则

以现有「网络连接不稳定」弹窗为例（全屏：警示图标 + 标题 + 正文「网络连接不稳定，请重试」+「重试」按钮，同类弹窗还带「OK」「去 WiFi 设置」等按钮）。**现状触发逻辑（工程确认，2026-07-07）**：① 请求后端接口连续 3 次超时；② TRTC SDK 回调网络差——两种信号共用同一个阻断弹窗，印证下述「轻重不分」问题。逐条问题：

- **文案零信息**：标题与正文重复，没说发生了什么、影响什么、系统正在做什么；
- **「重试」是机器的活**：重连应自动进行并自动重试，不应等待训练中的用户来点按钮；「OK」同理——用户确认了什么？
- **无归因**：WiFi 断了、宽带差、服务器异常，处理方式完全不同，但弹窗一概而论；
- **轻重不分**：瞬时抖动与彻底断线共用同一个全屏阻断样式；
- **恢复无反馈**：网络恢复后没有任何提示，用户可能已手动退课。

**收敛决策树（替代所有存量网络弹窗）：**

| 情况 | 判定信号 | 处理方式 | 用户操作 |
| --- | --- | --- | --- |
| **瞬时抖动**（< 10 秒自愈） | TRTC 自动重连成功 | 不打扰，最多黄灯角标 | 无 |
| **中断，自动重连中** | 断流 / quality = 6 | 非阻断横幅「网络中断，正在自动重连…」，课程画面定格 | 无（系统自动重试） |
| **重连超时或 WiFi 已断开**（> 30 秒） | 重试 N 次失败 / WiFi 离线 | 全屏中断页：归因文案 + 持续自动重试 + 单一动作按钮 | 仅「去 WiFi 设置」（系统做不了的事才给用户） |
| **恢复** | 重连成功 | toast「网络已恢复」自动消失，回到课程 | 无 |

**文案模板**（所有网络异常页统一四段式）：

1. **标题** = 发生了什么：「网络已断开」/「网络无法连接」；
2. **正文** = 影响 + 归因：「课程已暂停。WiFi 已断开」/「课程已暂停。已连接 WiFi，但无法访问网络」；
3. **辅助行** = 系统正在做什么：「正在自动重连（第 3 次）…」；
4. **按钮** = 只放用户才能做的事：「去 WiFi 设置」。**「重试」「OK」类按钮全部移除**。

> 收敛后全屏阻断页只剩一种：「彻底断线且自动重连持续失败」。其余场景一律角标 / 横幅 / toast，零操作。重设计后的全屏中断页与恢复 toast 示意图见 HTML 版。

### F5 质量数据上报与长期弱网通知（P2）

- **F5.1** 常驻检测按小时聚合上报（RSSI 分布、网关 / 服务器 RTT）；课中按会话聚合上报（各灯色时长占比、平均丢包 / RTT、降级触发次数）；完整检测逐次上报；
- **F5.2** 客服后台可按设备查询近 7 天网络质量时间线，区分「设备→路由器弱」「宽带弱」「服务端异常」三类归因；
- **F5.3** **长期弱网通知**：连续 3 天课中红灯累计超过阈值，向通知栏推送一条摆放建议，7 天内不重复推送；
- **F5.4** 阈值（§5）全部支持云端下发 / OTA 调整，首发取保守值，用上报数据校准。

### F6 手机 App · 课中网络状态提示（P1）

- **F6.1** 手机端沿用同一套灯色语义与防抖 / 冷却规则：绿灯完全隐藏，黄 / 红才出现；数据源为手机端 TRTC 回调（手机与 Atom 同在 TRTC 房间内，用远端流统计判 Atom 侧、`localQuality` 判手机侧）；
- **F6.2** **灯的锚定（定稿）——空间归因**：训练页有两路主画面（课件 / 教练视频，以及深色底的用户实时画面），网络灯**始终跟随用户实时画面窗口**（即 Atom 摄像头回传流）：用户画面在画中画时，灯挂在画中画角落；大小窗切换后用户画面成为主窗，灯跟着迁移到主窗角落。**默认语义 = 用户画面背后 Atom 的网络状态**。灯挂在哪路画面上，表达的就是那路流背后的网络，用户不读文字也能理解归因；
- **F6.2a** **手机侧弱网不挂窗口**：手机自身网络差影响的是整个页面（两路画面都卡），因此用页面级提示表达——toast「手机网络较差，建议切换网络」，不占用画面角标，与 Atom 侧提示天然区分；
- **F6.3** **角标形态随窗口尺寸变化**：用户画面为画中画（小窗）时，角标收缩为微型三格 bars（挂窗角）；切为主窗（大窗）时，展开为 bars + 短文案（如「Atom 网络较差」）。点按角标展开详情浮层：两端各自的状态 + 对应建议；灯色下降时 toast 一次（冷却 5 分钟，每节课最多 2 次），与设备端一致；
- **F6.4** **取代无解释的加载转圈**：用户画面（Atom 回传流）断流或加载超过 3 秒时，在该窗口内显示占位 + 归因文案（如「画面加载中 · Atom 网络较差」），不允许出现无限 spinner 而不解释原因（现状截图中已存在此问题）；教练视频 / 课件断流同理，归因到对应链路；
- **F6.5** 断线 / 重连遵循 F4-R 决策树：自动重连 + 横幅提示，恢复后 toast「网络已恢复」；记录训练数据类操作（如「记录本组」）在断网时本地缓存、恢复后自动同步，不阻塞用户；
- **F6.6** 手机端质量指标并入 F5 上报，与设备端同会话关联——客服可直接看到「卡顿发生时，弱的是哪一端」；
- **F6.7** **启动加载页（取代黑屏）**：进课时用户画面窗口的初始化过程目前是纯黑屏 loading，用户不知道系统在干什么。改为分阶段状态提示，依次「正在连接 Atom…」→「Atom 正在启动摄像头…」→ 出画面；任一阶段超过 5 秒未推进，追加一行原因（如「网络较慢，仍在加载…」）；连接失败进入 F4-R 决策树（自动重试 +「正在重连…」）。加载标识使用 Atom 形象（双眼），与设备待机脸一致。原则：**任何等待都必须告知系统正在做什么**，一行状态 + 一行原因，不超过两行。

手机端两种状态的界面示意图（小窗态灯点挂画中画角落、大窗态角标随用户画面迁移并展开文案）见 HTML 版。

### F7 常驻监测调度与数据时效（P0）

- **F7.1** **采样时机（会议 2026-07-07 对齐）**：① 首次配网成功 → 静默采样一次；② 开机完成 / 休眠唤醒 → 采样一次；③ 亮屏交互态 → 每 30 秒轻探测（F2.4a）；④ 桌面常亮态（时钟 / 待机画面）→ 每 60 分钟低频采样一次（OTA 可调 30–120 分钟）；⑤ 进课前 → 必采样；
- **F7.2** **熄屏 / 待机不采样**：不为测网主动唤醒设备（续航优先）——长时间闲置期间没有样本是预期行为，依赖下次唤醒时的补测（F7.1-①）；
- **F7.3** **时效规则**：每个样本带时间戳，新鲜窗口 5 分钟；过期样本一律不外显灯色（各入口显示「检测中…」并触发刷新）——宁可短暂灰色，不用旧结论冒充现状；
- **F7.4** **时效外显只在小程序首页**（「刚刚更新 / N 分钟前更新」）。WiFi 状态行、通知栏、控制中心不显示时间戳——这些入口只在亮屏时可见，而亮屏时数据必然 ≤30 秒旧：**「看得见即新鲜」**，时间戳在那里是冗余信息；
- **F7.5** **连续弱网主动提示（短期，会议提出）**：同一 WiFi 下连续 3 次采样为黄 / 红 → 通知栏推送一条「当前 WiFi 网速较弱，可能影响上课」（每个 WiFi 每天最多一次；绿灯永不主动提示）。采样历史按 SSID 记录，弱网判定与所连 WiFi 绑定，支撑 F3.6 历史记录与 F5.2 客服归因；与 F5.3 的长期弱网通知（连续 3 天课中红灯）分层：F7.5 管「这几个小时」，F5.3 管「这几天」。

## 5. 状态机与阈值（首发值，OTA 可调）

| 灯色 | 课中（TRTC quality） | 常驻（RSSI） | 常驻（RTT / 丢包） |
| --- | --- | --- | --- |
| 绿 | 1–2（Excellent / Good） | > −60 dBm | RTT < 50 ms 且丢包 < 2% |
| 黄 | 3–4（Poor / Bad） | −60 ~ −70 dBm | RTT 50–150 ms 或丢包 2–8% |
| 红 | 5–6（VeryBad / Down） | < −70 dBm | RTT > 150 ms 或丢包 > 8% |

- **多指标合并**：取各指标判定结果中的**较差者**作为最终灯色；
- **防抖**：连续 3 个采样周期落在同一级才切换灯色（课中约 6 秒，常驻约 90 秒），避免闪烁；
- **提示冷却**：课中弱网 toast 冷却 5 分钟，每节课最多 2 次；灯色变好不提示，只静默变绿；
- **归因探测**：常驻检测同时 ping 网关与自家服务器——网关差 = 设备→路由器段弱（建议挪位置）；网关好而服务器差 = 宽带 / 公网段弱（建议换网络或错峰）。

### 5.1 完整检测 · TRTC 接口对齐（开发对接）

调用参数（`startSpeedTest` / `TRTCSpeedTestParams`）：

| 调用参数 | 取值 | 依据 |
| --- | --- | --- |
| `scene` | delayAndBandwidthTesting（延迟 + 带宽双测） | 波形图与「上行流畅」判定需要带宽预测 |
| `expectedUpBandwidth` | **1500 kbps**（范围 10–5000） | Atom 上行摄像头 720p@15fps 官方推荐码率 1200 kbps + 25% 余量 |
| `expectedDownBandwidth` | **2000 kbps** | 下行课件 / 教练视频 720p 推荐码率 + 余量；升级 1080p 需同步上调 |
| `sdkAppId / userId / userSig` | 复用业务账号体系 | 官方必填 |

结果字段映射（`TRTCSpeedTestResult` → UI）：

| 字段 | 单位 / 范围 | UI 呈现 |
| --- | --- | --- |
| `quality` | TRTCQuality 1–6 | **灯色直接采用官方综合评分**：1–2 绿 / 3–4 黄 / 5–6 红（与课中 `onNetworkQuality` 同一映射）；本地 RTT / 丢包阈值仅用于常驻轻探测 |
| `rtt` | ms | 「延迟」数值 |
| `upLostRate / downLostRate` | 0–1.0 | 「丢包」= 较大值 ×100%；分列数据入详情与上报 |
| `availableUpBandwidth` | kbps，-1 无效 | 「上行」：≥ 期望值 →「流畅」；不足 → 显示实测 kbps；-1 →「—」 |
| `availableDownBandwidth` | kbps，-1 无效 | 下行曲线与结果，比较逻辑同上 |
| `success / errMsg` | — | 失败态「检测未完成 · 请重试」；errMsg 仅上报 |
| `ip` | — | 不上屏，随 F5 上报 |

- **进度与波形粒度**：官方按测速节点每 2–3 秒回调一个样本，整次约 10–20 秒——环形进度按 `finishedCount / totalCount` 真实驱动（不做假进度）；波形逐点绘制（约 5–8 个点）平滑连线；
- **官方约束互证**：仅进房前调用（= F3.5 课中互斥）；同一时间仅一个测速任务（按钮防重入）；测速产生少量基础服务费（仅用户主动触发）；
- **附加收益**：测速结果被 SDK 用于后续**选路优化**——课前测速能让下节课选到更优节点，可在 tips 页告知用户；
- **实现路径（会议 2026-07-07）**：`startSpeedTest` 在非课中场景的可用性待工程实测（官方文档定位即为「进房前测速」，与我们的使用场景一致，但需在当前 SDK 版本验证，见 §8 风险表）；**备选方案**为自研文件测速（对自家服务器上传 + 下载测试文件、数秒内多次采样，参考 PC 教练端现有实现）。两种实现共用同一套 UI、状态机与文案——切换实现不影响本 PRD 其余部分。

英文文案原则：**状态不重复**——灯点 / 位置已表达严重程度与归因时，文字只补充新信息（如 toast 直接说后果 "Your video may lag"，不再重复 "Weak network"）；**动作词单一**——按钮用单词（Retest / Full test）；统一 "Wi-Fi" 拼写。

## 7. 埋点与成功指标

- **北极星**：网络类客诉占比下降 ≥ 30%（以「卡顿」关键词客诉为基线）；
- 检测功能触达：小程序周打开率、三个入口各自的点击占比；
- 问题发现：红灯设备占比、红灯设备中收到建议后 7 天内 RSSI 改善（挪动了设备）的比例；
- 体验兜底：课中红灯时长占比环比变化（衡量降级 + 引导的综合效果）。

## 8. 依赖与风险

| 项 | 说明 | 应对 |
