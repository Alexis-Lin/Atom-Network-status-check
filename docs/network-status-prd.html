网络状态「红绿灯」— 弱网可感知与网络验证

版本V0.12 草稿 日期2026-07-05 状态评审中 涉及端ATOM 设备（466×466 圆屏）· 手机 App · 云端上报服务

1背景与问题

ATOM 是一台通过 WiFi 联网的嵌入式训练设备，上课时通过 TRTC 进行实时音视频互动（含摄像头画面上行）。当前用户反馈的核心问题：设备已连上 WiFi，但上课时仍然卡顿。

  • 「已连接 WiFi」≠「网络够用」。信号衰减、家庭宽带上行不足、路由器负载等都会导致卡顿，但设备目前对用户只呈现「已连接」一种状态；
  • 用户卡顿时无法归因，默认判定为「阿童木做得卡」，产生客诉；客服排查也缺少依据；
  • ATOM 是固定摆放设备，信号好坏在摆放时即已决定，但用户没有任何工具能发现「摆放位置信号弱」这一问题。

1.1 现有机制及其问题

设备目前已有若干网络慢 / 异常提示，但全部是课中真的出了问题之后才触发的弹窗，且部分弹窗需要用户手动点击确认才能关闭。这带来三个问题：

  • 时机太晚：提示出现时体验已经受损，用户没有任何机会在课前预防；
  • 形式太重：阻断式弹窗遮挡训练画面，把「网络卡」升级成「课被打断」；
  • 操作不可行：用户正在做训练动作、距屏幕较远，要求手动点确认基本等于强制中断训练——提示本身成了负体验。

因此本方案不只是「新增红绿灯」，同时要收敛存量课中弹窗：把网络提醒从「课中事后打断」改造为「课前可预防、课中不打断」。

2目标与非目标

2.1 目标

  • 可感知：用户在任意时刻都能一眼看到当前网络对上课「够不够用」（红绿灯三态）；
  • 可验证：用户可以主动发起一次网络验证，获得针对上课链路的真实测速结果；
  • 可行动：网络差时给出可执行建议（靠近路由器 / 切换 WiFi / 重测），而非只报忧；
  • 不打断：课中网络提示全部改为非阻断、自动消失、零操作；需手动确认的弱网弹窗全部移除；
  • 可归因：质量数据上报云端，支撑客服排查与阈值校准，降低网络类客诉。

2.2 非目标

  • 不承诺「解决」用户的网络问题（宽带质量不在我们控制内），本期解决的是感知、归因与引导；
  • 不做持续带宽测速（会挤占上课带宽）；不做路由器侧诊断与配置；
  • 课中自适应降级（流畅优先、音频优先）依赖 TRTC 既有能力，本 PRD 只要求正确配置并在文案中告知用户，不新增自研弱网算法。

3方案总览

一套「红绿灯」状态机 + 一个网络验证小程序，通过四个触点触达：

  1. 上拉通知栏（设备）：常驻网络状态条目，点击进入网络验证小程序；
  2. WiFi 图标与 WiFi 菜单（设备）：控制中心 WiFi 磁贴角标 + WiFi 设置页状态行；
  3. 网络验证小程序（设备）：独立小程序，秒开当前状态 + 可发起完整测速；
  4. 手机 App 课中提示：训练页面同步展示网络状态，并归因到「手机侧 / Atom 侧」。

所有触点共享同一个状态机语义与阈值，保证任何入口看到的灯色一致。与现状的关系一览：

维度现状本方案
触发时机课中已经出问题才提示常驻可见 + 课前可验证 + 课中实时
提示形式阻断式弹窗，遮挡训练画面常驻灯色 / 角标 / 自动消失 toast
用户操作部分需手动点击确认零操作；仅「需用户决策」的场景保留弹窗
问题定位无归因，只报「网络异常」分段归因（设备→路由器 / 宽带→公网）+ 可执行建议

3.1 灯的三态定义

绿 · 网络良好

上课体验预计流畅。静默显示，不打扰用户。

黄 · 网络一般

可以上课，可能偶尔卡顿。课中触发流畅优先降级并轻提示。

红 · 网络较差

上课大概率卡顿。提示并给出可执行建议。

3.2 检测数据源分工

场景数据源频率流量成本
常驻（通知栏 / WiFi 图标 / WiFi 菜单）系统 RSSI + ping 网关与自家服务器30 秒静默刷新几乎为零
主动验证（小程序完整检测）TRTC startSpeedTest（到 TRTC 边缘节点）用户触发，单次约 15 秒少量真实测速流量；课中禁止调用
课中TRTC onNetworkQuality + onStatisticsSDK 每 2 秒回调零（复用业务流量）

原则：不为了检测而挤占上课带宽。常驻状态只用被动/轻量数据；真实测速只在用户主动发起且不在课中时执行。

F3 网络验证小程序P0

  • F3.1独立小程序，出现在应用列表中；F1 / F2 的入口均跳转至此；
  • F3.2秒开首页（准实时）：进入即展示常驻检测缓存（数据最旧不超过 30 秒），同时立即触发一次轻量刷新（ping，1~2 秒内原地更新灯色与指标）；无有效缓存时显示「检测中…」直至刷新完成。首页指标来自常驻轻探测，上课真实链路的测速由「完整检测」提供；

  • F3.4结果页三态（绿 / 黄 / 红各有独立结果页）。黄 / 红结果必须包含：弱在哪一段（本机→路由器 / 路由器→公网）、一条可执行建议；按钮遵循 F3.7；

F4 课中实时角标、弱网提示与存量弹窗收敛P1

  • F4.1课中以 TRTC onNetworkQuality 为唯一灯色数据源（每 2 秒回调，上行 localQuality 与下行 remoteQuality 取较差者）；
  • F4.2绿灯时角标完全隐藏；变黄 / 红时在屏幕顶部显示信号角标；
  • F4.3灯色下降时弹出一次 toast，文案区分方向：上行差 →「网络较差 · 你的画面可能卡顿」；下行差 →「网络较差 · 课程画面可能卡顿」；黄灯统一为「网络一般 · 已降低画质」；
  • F4.4确认 TRTC 弱网降级配置：setNetworkQosParam 流畅优先、音频优先兜底、上行编码参数留余量（720p），降级动作通过 F4.3 文案让用户可感知；
  • F4.5课中每 2 秒的 onStatistics 明细（RTT / 上下行丢包 / 码率）聚合后随课程会话上报（F5），不在 UI 展示；
  • F4.6存量弹窗收敛：盘点现有课中网络类弹窗，按「是否需要用户决策」分级——仅「彻底断线且无法自动恢复、需用户选择重连 / 退出」类保留阻断式弹窗；其余全部替换为本方案的角标 + 自动消失 toast；移除所有需手动点击确认的弱网提示；
  • F4.7提示可感知性：训练中用户处于动作中、距屏幕较远，视觉 toast 可能看不到——黄 / 红提示同步配一个短音效或简短语音播报（如「网络不稳定」），确保不看屏幕也能感知；音量跟随媒体音量，可在设置中关闭。

F4-R 存量弹窗 Review 与收敛规则

以现有「网络连接不稳定」弹窗为例（全屏：警示图标 + 标题 + 正文「网络连接不稳定，请重试」+「重试」按钮，同类弹窗还带「OK」「去 WiFi 设置」等按钮）。逐条问题：

  • 文案零信息：标题与正文重复，没说发生了什么、影响什么、系统正在做什么；
  • 「重试」是机器的活：重连应自动进行并自动重试，不应等待训练中的用户来点按钮；「OK」同理——用户确认了什么？
  • 无归因：WiFi 断了、宽带差、服务器异常，处理方式完全不同，但弹窗一概而论；
  • 轻重不分：瞬时抖动与彻底断线共用同一个全屏阻断样式；
  • 恢复无反馈：网络恢复后没有任何提示，用户可能已手动退课。

收敛决策树（替代所有存量网络弹窗）

情况判定信号处理方式用户操作
瞬时抖动（< 10 秒自愈）TRTC 自动重连成功不打扰，最多黄灯角标无
中断，自动重连中断流 / quality = 6非阻断横幅「网络中断，正在自动重连…」，课程画面定格无（系统自动重试）

文案模板（所有网络异常页统一四段式）：

  • 标题 = 发生了什么：「网络已断开」/「网络无法连接」；
  • 正文 = 影响 + 归因：「课程已暂停 · WiFi 已断开」/「课程已暂停 · 已连 WiFi，无法访问互联网」；
  • 辅助行 = 系统正在做什么：「正在自动重连（第 3 次）…」；
  • 按钮 = 只放用户才能做的事：「去 WiFi 设置」。「重试」「OK」类按钮全部移除。

收敛后全屏阻断页只剩一种：「彻底断线且自动重连持续失败」。其余场景一律角标 / 横幅 / toast，零操作。

F5 质量数据上报与长期弱网通知P2

  • F5.1常驻检测按小时聚合上报（RSSI 分布、网关 / 服务器 RTT）；课中按会话聚合上报（各灯色时长占比、平均丢包 / RTT、降级触发次数）；完整检测逐次上报；
  • F5.2客服后台可按设备查询近 7 天网络质量时间线，区分「设备→路由器弱」「宽带弱」「服务端异常」三类归因；
  • F5.3长期弱网通知：连续 3 天课中红灯累计超过阈值，向通知栏推送一条摆放建议（右图），7 天内不重复推送；
  • F5.4阈值（§5）全部支持云端下发 / OTA 调整，首发取保守值，用上报数据校准。

F6 手机 App · 课中网络状态提示P1

  • F6.1手机端沿用同一套灯色语义与防抖 / 冷却规则：绿灯完全隐藏，黄 / 红才出现；数据源为手机端 TRTC 回调（手机与 Atom 同在 TRTC 房间内，用远端流统计判 Atom 侧、localQuality 判手机侧）；
  • F6.2灯的锚定（定稿）——空间归因：训练页有两路主画面（课件 / 教练视频，以及深色底的用户实时画面），网络灯始终跟随用户实时画面窗口（即 Atom 摄像头回传流）：用户画面在画中画时，灯挂在画中画角落；大小窗切换后用户画面成为主窗，灯跟着迁移到主窗角落。默认语义 = 用户画面背后 Atom 的网络状态。灯挂在哪路画面上，表达的就是那路流背后的网络，用户不读文字也能理解归因；
  • F6.2a手机侧弱网不挂窗口：手机自身网络差影响的是整个页面（两路画面都卡），因此用页面级提示表达——toast「手机网络较差 · 建议更换网络」，不占用画面角标，与 Atom 侧提示天然区分；
  • F6.3角标形态随窗口尺寸变化：用户画面为画中画（小窗）时，角标收缩为一个灯点（挂窗角）；切为主窗（大窗）时，展开为灯点 + 短文案（如「Atom 网络较差」）。点按角标展开详情浮层：两端各自的状态 + 对应建议；灯色下降时 toast 一次（冷却 5 分钟，每节课最多 2 次），与设备端一致；
  • F6.4取代无解释的加载转圈：用户画面（Atom 回传流）断流或加载超过 3 秒时，在该窗口内显示占位 + 归因文案（如「画面加载中 · Atom 网络较差」），不允许出现无限 spinner 而不解释原因（现状截图中已存在此问题）；教练视频 / 课件断流同理，归因到对应链路；
  • F6.5断线 / 重连遵循 F4-R 决策树：自动重连 + 横幅提示，恢复后 toast「网络已恢复」；记录训练数据类操作（如「记录本组」）在断网时本地缓存、恢复后自动同步，不阻塞用户；
  • F6.6手机端质量指标并入 F5 上报，与设备端同会话关联——客服可直接看到「卡顿发生时，弱的是哪一端」；
  • F6.7启动加载页（取代黑屏）：进课时用户画面窗口的初始化过程目前是纯黑屏 loading，用户不知道系统在干什么。改为分阶段状态提示，依次「正在连接 Atom…」→「Atom 正在启动摄像头…」→ 出画面；任一阶段超过 5 秒未推进，追加一行原因（如「网络较慢，仍在加载…」）；连接失败进入 F4-R 决策树（自动重试 +「正在重连…」）。原则：任何等待都必须告知系统正在做什么，一行状态 + 一行原因，不超过两行。

5状态机与阈值（首发值，OTA 可调）

灯色课中（TRTC quality）常驻（RSSI）常驻（RTT / 丢包）
绿1–2（Excellent / Good）> −60 dBmRTT < 50 ms 且丢包 < 2%
黄3–4（Poor / Bad）−60 ~ −70 dBmRTT 50–150 ms 或丢包 2–8%
红5–6（VeryBad / Down）< −70 dBmRTT > 150 ms 或丢包 > 8%
  • 多指标合并：取各指标判定结果中的较差者作为最终灯色；
  • 防抖：连续 3 个采样周期落在同一级才切换灯色（课中约 6 秒，常驻约 90 秒），避免闪烁；
  • 提示冷却：课中弱网 toast 冷却 5 分钟，每节课最多 2 次；灯色变好不提示，只静默变绿；
  • 归因探测：常驻检测同时 ping 网关与自家服务器 —— 网关差 = 设备→路由器段弱（建议挪位置）；网关好而服务器差 = 宽带 / 公网段弱（建议换网络或错峰）。

6状态文案表（双语）

文案原则：一行说清，状态在前、动作在后。词族划分：测速场景用「网速」（状态行 / 通知栏 / 小程序——快慢问题），连接场景用「网络」（课中中断 / 重连 / 恢复——通断问题）。英文原则：状态不重复——灯点 / 位置已表达严重程度与归因时，文字只补充新信息（toast 直接说后果，如 "Your video may lag"）；按钮用单词（Retest / Full test）；统一 "Wi-Fi" 拼写。

7埋点与成功指标

  • 北极星：网络类客诉占比下降 ≥ 30%（以「卡顿」关键词客诉为基线）；
  • 检测功能触达：小程序周打开率、三个入口各自的点击占比；
  • 问题发现：红灯设备占比、红灯设备中收到建议后 7 天内 RSSI 改善（挪动了设备）的比例；
  • 体验兜底：课中红灯时长占比环比变化（衡量降级 + 引导的综合效果）。
